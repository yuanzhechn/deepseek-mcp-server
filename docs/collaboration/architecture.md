# Collaboration architecture (Phase 0–2)

Codex/GPT remains the host. This MCP server controls only DeepSeek requests; it cannot invoke subscription GPT, inspect its true remaining quota, change the host model, execute shell commands or apply patches. The original eleven tools remain registered with their original inputs. Seven tools are added: `list_collab_profiles`, `get_collab_status`, `set_collab_profile`, `route_task`, `delegate_task`, `estimate_task_cost`, `get_usage_report`.

`ProfileStore` → `PolicyEngine` → `TaskRouter` → `CollaborationService` → existing `DeepSeekApiClient`. Before every generation, including legacy chat/FIM/Responses, the service reads a fresh policy, validates context and reserves the worst-case cost in SQLite. Provider usage is normalized, priced with the admitted catalog snapshot and settled once. Structured receipts carry provider model/request ID, trace/task ID, policy revision, raw and normalized usage, estimated cost and duration. Read-only metadata operations do not consume token budgets. Uploads receive the profile/data gate because they transmit content, but have no modeled token cost.

`route_task` is a deterministic, non-generating recommendation. It reports cold-start heuristic reasons, approximate input/output costs and required review. `gpt` returns `host_required`. `delegate_task` reroutes from a fresh snapshot and requires a unique task ID, task type/risk, nonempty requirements, acceptance criteria, bounded snippets, output/total token ceilings and deadline. It returns a candidate artifact as text, never a file write or an assertion that tests passed. No function tools are supplied to a delegate, depth is zero, and attempts are bounded to three.

Storage is per local operator: `profiles.json` (versioned schema, revision, lock and atomic rename) and `usage.sqlite` (WAL, immediate reservation transactions). HTTP reuses one collaboration service across its stateless MCP server factories. Each tool shares the preexisting client-scoped admission rate limiter. A running request retains its admitted snapshot; a subsequent call observes CLI changes without restarting the server.

Configuration and prices have exported version 1 JSON Schemas generated from runtime Zod validation. Unknown schema versions fail closed. No prompts, generated output or credentials are stored in the usage ledger. Conversation history remains a separate process-local Map; it is screened again when replayed to DeepSeek.

Budget amounts use integer nanodollars and Beijing calendar days. Reservations include all input bytes plus conservative framing, maximum requested/default output, maximum peak/off-peak rates and zero assumed cache hits. Opaque image/file references reserve a full context window. Uncertain and in-flight reservations count even across midnight. Provider usage is authoritative for token counts; prices yield an estimated bill, not an account statement. Missing cache details conservatively assume no cache hits. Missing/invalid usage or unknown provider model prices retain the reservation.

Explicit 429 admission rejection may be retried with exponential delay/jitter within the same reservation (at most two retries, opt-in via delegation `max_attempts`). 401/403 are not retried. Network/5xx/timeout/cancellation can have incurred charges, so they are not automatically resent and retain a hold. This deliberately resolves the design's retry/idempotency tension in favor of avoiding duplicate paid work.

Price source: [DeepSeek pricing](https://api-docs.deepseek.com/quick_start/pricing/), verified 2026-11-01. Input cache usage fields: [Chat API](https://api-docs.deepseek.com/api/create-chat-completion/). The catalog supports official UTC weekday peak windows and operator-supplied Chinese public holiday dates. The bundled calendar is explicitly incomplete: weekday peaks may conservatively overstate holiday prices. A complete, verified calendar can be supplied in `DEEPSEEK_COLLAB_PRICE_FILE` without code changes. Search/Fetch rates are recorded in the catalog, but no standalone Search/Fetch endpoint is exposed and server-side `web_search` is policy-blocked: its independent request count cannot currently be bounded or observed reliably. The host performs live research.

Phase 3 design: a separate local tray/localhost UI would use these operator interfaces, with independent authentication/origin protection. Phase 4 design: isolated worktrees, allowlisted validators, candidate diff review, bounded DAG scheduling and explicit integration. Neither phase is implemented or enabled by this change.
